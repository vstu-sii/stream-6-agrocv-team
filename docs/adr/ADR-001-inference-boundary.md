# ADR-001. Распознавание внутри серверного приложения

**Статус:** Принято (проектное решение). **Дата:** 31.10.2026. **Обновлено:** 02.11.2026.

## Контекст

MVP включает один тип входа, четыре класса и синхронный пользовательский разбор. Нужны проверяемые ошибки, p95 до 10 секунд и таймаут 20 секунд. Фактические ресурсы модели и размещения пока неизвестны. Существующая модель используется без изменения, если подходит; дообучение при необходимости проводится вне обработки пользовательских запросов.

## Решение и структурная схема

Браузерный клиент обращается к API. API содержит внутренний модуль распознавания: предобработка, запуск версии модели, проверка выхода, сопоставление классов и решение об отказе. Модель Qwen3-VL-4B-Instruct используется с версионированными процессором, промптом и схемой результата. Это генеративная мультимодальная модель, а не подтверждённый классификатор болезней; её качество на четырёх классах проверяется отдельно.

Схема зависимостей: `Браузер → API → внутренний модуль распознавания → веса модели`. Модуль не является самостоятельным сетевым сервисом. Веб-интерфейс и API поставляются в Docker; модель исполняется внутри серверного приложения. Состав Compose и проверки — в [deployment.md](../deployment.md). Обучение/дообучение и загрузка новых весов не запускаются по пользовательскому запросу. Справочные тексты выдаёт приложение из проверенных карточек, а не свободная генерация модели.

API отвечает за валидацию запроса, время обработки и отсутствие дублирующих попыток; модуль распознавания — за вызов Qwen3-VL-4B-Instruct, проверенный структурированный ответ и допустимые классы. Технология API, формат весов и конкретная библиотека определяются AI Engineer и Delivery после проб.

## Альтернативы

- **Отдельный сервис распознавания:** независимое масштабирование и среда ML, но дополнительный сетевой контракт, развёртывание и диагностика отказов. Нужен при фактическом конфликте ресурсов или зависимостей, пока не доказанном.
- **Внешний inference-API:** меньше локальной инфраструктуры, но передача фото третьей стороне, ограничения провайдера и нестабильная стоимость. Не выбран для текущей схемы; возможный переход потребует отдельного ADR и изменения модели угроз.
- **Распознавание на телефоне:** меньше серверной обработки, но зависимость от устройства и доставки весов; ресурсы и совместимость модели с телефонами аудитории не проверены.

## Обоснование

Внутренний модуль уменьшает число сетевых отказов в небольшом MVP и позволяет контролировать формат результата, версию и отказ в одной серверной границе. Отделение ML в самостоятельный сервис откладывается до измеренной необходимости. Внутренняя граница не требует многоуровневой фабрики адаптеров; нужна проверка входа/выхода и явная ответственность.

## Цена решения

**Принятый компромисс:** уменьшаем число сетевых границ MVP ценой общего процесса, ресурсов и выпуска API с моделью.

| Вид цены | Конкретное последствие | Как учитываем |
| --- | --- | --- |
| Ограничение | Нельзя отдельно масштабировать или обновлять Qwen без изменения серверного контура | При необходимости независимого выпуска пересматриваем ADR |
| Риск доступности | Исчерпание памяти или блокировка моделью может затронуть API и пользовательский ответ | Проверяем нагрузку, таймауты и поведение при сбое |
| Эксплуатационные затраты | Сервер должен держать веса и процессор Qwen, совместимые зависимости и необходимые CPU/GPU-ресурсы, включая простой | Фактическую стоимость оцениваем на выбранном размещении по AC-07 |
| Цена изменения | Выделение модели в сервис потребует сетевого контракта, конфигурации Compose и повторной интеграционной проверки | Выполняем только при измеренной необходимости |

- Весам и API нужны общая среда выполнения и совместимые зависимости.
- Память и CPU/GPU общие; тяжёлая модель может блокировать запросы и вынудить пересмотр границы.
- Выпуск модели связан с выпуском приложения; для обновления нужна воспроизводимая версия артефакта.
- Нет независимого масштабирования распознавания. Допустимый параллелизм определяется замером, а не обещанием из диаграммы.
- Если готовая модель не помещается в ограничения, переход к отдельному сервису потребует нового сетевого контракта и доработки тестов.

Денежные расходы измеряются после выбора хостинга, квантования и ресурсов. Цель AC-07 — не более 0,50 ₽/принятый запрос при 1 000 запросов/месяц с учётом инфраструктурного простоя и ошибок. Это целевой предел, а не оценка или подтверждённый тариф. Дообучение учитывается отдельно; перечисленные ограничения и риски принимаются независимо от будущего денежного замера.

## Как проверить соблюдение

- UC-01/UC-02, AC-01, AC-03–AC-07: проверка схемы, неподходящего файла, невалидного выхода, таймаута, качества и задержки.
- Проверить, что пользовательский запрос не запускает обучение и не скачивает новые веса из непроверенного источника.
- Проверить версию, соответствие классов и предобработку при каждой смене модели.
- Delivery отражает модуль как компонент внутри API на детализации, а не отдельный контейнер C4; контейнерная схема показывает браузерный клиент, API и необходимые хранилища.
- Согласовать применимость правил aact к фактической структуре; успешный запуск здесь не заявляется.

## Условия пересмотра

Невозможность выдержать время/ресурсы, необходимость независимого выпуска ML, несколько разных потребителей распознавания или переход к внешнему провайдеру.
