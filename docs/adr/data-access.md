# Хранилище диагнозов принадлежит одному владельцу — репозиторию

**Статус:** Принято
**Дата:** 2026-10-22
**Роль:** Delivery
**Схема:** [C4 контейнеров](../architecture/c4-container.puml), [ERD](../architecture/erd.puml)

## Контекст

Нужно хранить снимки фото, диагнозы, назначения и журнал обработок. В
команде четыре роли, и к лабе 3 к базе могут потянуться и API-сервис, и
воркер. Общая база «для всех» — самый быстрый способ начать, и самый
дорогой в сопровождении: неясно, кто владеет схемой, кто отвечает за
миграции, и любая правка одной таблицы ломает чужой код.

Варианты:

- **одна общая база, все ходят в неё напрямую**;
- **база с одним владельцем, остальные — через его API** — выбрано;
- **база на каждый сервис** (классический database-per-service).

## Решение

### Схема

```
api → diagnostics_repo ($tags="repo") → diagnostics_db
```

### Обоснование

- Владелец данных один: `diagnostics_repo`. Только он ходит в
  `diagnostics_db`, и только он меняет схему.
- API-сервис и воркер не знают про SQL: они говорят с репозиторием через
  доменный интерфейс. Смена хранилища (PostgreSQL → другое) не задевает
  вызывающий код.
- Одна база, а не база на сервис: в MVP пишет один компонент, плодить
  хранилища — лишняя операционная работа без выигрыша.

## Цена решения

Берём на себя: «узкое горлышко» — репозиторий должен покрывать все
потребности читателей, иначе постоянно правки; риск раздувания
репозитория в «базу данных в коде»; отсутствие независимых схем на
компонент, если позже разделим систему. Альтернатива «база на сервис»
дала бы изоляцию, но в MVP обернулась бы лишней инфраструктурой и
кросс-сервисными join'ами по снимкам и диагнозам.

## Последствия

- Миграции схемы живут в одном месте (`database/schema.sql` и каталог
  миграций) и принадлежат роли Delivery.
- Новый потребитель данных получает данные через репозиторий или через
  API-сервис, а не чтением из базы.
- Если появится второй владелец данных — решение пересматривается, это
  будет новый ADR.

## Как покрыть тестами

- `database/schema.sql` применяется к пустой базе без ошибок (смоук-проверка
  в лабе 3).
- Миграция «вперёд» применяется повторно без падений.
- Интеграционный сценарий: диагноз записан через API → прочитан через API.

## Чем это проверяется машиной

Правила `crud` и `dbPerService` в `aact.config.ts`: к базе ходит только
контейнер с тегом `repo`, и у каждой базы ровно один владелец.
