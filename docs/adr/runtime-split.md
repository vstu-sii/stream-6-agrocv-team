# Разделить обработку диагностики на API-сервис и AI-воркер

**Статус:** Принято
**Дата:** 2026-10-22
**Роль:** Delivery
**Схема:** [C4 контейнеров](../architecture/c4-container.puml)

## Контекст

Задача MVP — по фото листа получить диагноз и назначение обработки. Один
запрос занимает секунды: модель распознаёт растение, ставит диагноз и сверяет
назначение со справочником. Обработка упирается во внешние API с лимитами и
нестабильным откликом, поэтому «просто подождать» в HTTP-запросе плохо.

Возможные варианты:

- **монолит** — весь пайплайн внутри API-сервиса;
- **API-сервис + AI-воркер через очередь** — что выбрано;
- **синхронный вызов воркера по HTTP** — воркер как отдельный сервис, но
  клиент ждёт ответа.

## Решение

### Схема

```
клиент → web → api → [queue] → ai_worker → адаптеры → внешние системы
                       ↑                    │
                       └── репозиторий ←───┘
```

### Обоснование

- Воркер вынесен в отдельный процесс: обработка длинная и может повторяться
  (ошибка внешнего API), а HTTP-запрос клиента не должен висеть.
- Очередь вместо синхронного вызова: клиент получает `id` задачи сразу и
  забирает статус, пока идёт диагностика.
- В API-сервисе остаётся всё, что должно отвечать синхронно: приём фото,
  постановка задачи, выдача результата.

## Цена решения

Берём на себя: отдельный процесс и развёртывание, брокер сообщений (Redis)
в инфраструктуре, eventual consistency результата (клиент узнаёт о диагнозе
не мгновенно), два места, где надо поддерживать контракт задачи, и
отладку «зависшей» очереди. Простой монолит дал бы меньше движущихся частей,
но блокировал бы клиента на время внешнего вызова.

## Последствия

- Повтор задачи после сбоя — обязанность воркера (идемпотентность по `id`).
- Метрики очереди (длина, возраст задач) становятся частью наблюдаемости.
- Если в лабе 3 выяснится, что медиана ответа меньше секунды, схема
  «очередь» может оказаться лишней — решение пересматривается в ADR.

## Как покрыть тестами

- Проверка живости контейнеров в `compose.dev.yml` (healthcheck) — воркер
  поднимается и отвечает.
- Интеграционный сценарий: задача положена в очередь → результат появился в
  базе (зона роли Quality, тест-план лабы 2).
- В CI: `docker compose -f compose.dev.yml config -q` — скелет окружения
  остаётся валидным.

## Чем это проверяется машиной

Правило `acyclic` в `aact.config.ts` — в графе зависимостей нет циклов
(`web → api → queue ← ai_worker → адаптеры`).
