# DoD артефактов команды — лабораторная 2

Проект: AgroCV — диагностика болезней растений по фото.  
Репозиторий: https://github.com/vstu-sii/stream-6-agrocv-team  
Назначение: определить до реализации, какими проверками подтверждается готовность каждого результата команды.

## 1. Основание и область проверки

Перечень артефактов взят из задания лабораторной 2 для Product / VO, AI Engineer, Delivery и Quality & Safety. Проверяется каждый результат по указанному пути, а не только документы Quality. ADR — общий результат Product и Delivery: проверяется один и тот же набор записей, без дублирования.

Анализируются только листья. Другие органы и дерево целиком допускаются лишь в отрицательных тестах. Результат по листу не означает здоровье всего дерева и не подтверждает безопасность урожая.

В материалах есть расхождение, требующее решения команды:

| Параметр | Ранее заданная область Quality | PRD и бриф в репозитории |
|---|---|---|
| Культура | Яблоня и вишня | Только яблоня |
| Результат | Вероятная болезнь и обоснованные рекомендации | Четыре класса: healthy, apple_scab, black_rot, cedar_apple_rust; cannot_assess — отказ, а не обученный класс |
| Лечение | Предусматривалась проверка назначений | Автоматическое назначение лечения исключено из MVP |
| Проверка качества | План 10 dev + 40 контрольных случаев, точность ≥85% | Macro-F1 ≥0,80 на независимых бытовых фото: ≥60, ≥15 каждого класса |
| Задержка | p95 ≤15 с, конкурентность 1 | p95 ≤10 с при 5 одновременных пользователях, ≥100 запросов |
| Тайм-аут | 60 с | 20 с |
| Стоимость | Переменные затраты ≤1 ₽ за запрос | Инфраструктура обработки ≤0,50 ₽ за принятый запрос при 1 000 запросов/месяц |

Это разные определения объёма и измерений, а не взаимозаменяемые числа. DoD не разрешает противоречие самостоятельно. Product и команда фиксируют выбранные культуру, классы, допустимые ответы и метрики; затем синхронизируют зависимые файлы. До этого согласованность не считается подтверждённой. Упоминание вишни здесь не означает её принятие в MVP или её исключение по решению Quality.

README содержит общее описание диагностики и лечения, а PRD ограничивает результат предварительной оценкой без назначений. Пользовательские обещания также приводятся к выбранной области.

## 2. Как выполняется проверка

Каждое условие имеет ID, точный объект и машинно проверяемый предикат. Слова «достаточно», «качественно», «понятно» без рубрики не используются. Факт наличия поля и истинность его содержания проверяются раздельно.

Проверяющий использует:

- Парсеры JSON/YAML/OpenAPI, SQL и исходных схем, проверки существования файлов и разрешения ссылок.
- Подсчёт записей, проверку уникальности ID, обязательных полей, перечислений и связей между артефактами.
- Пересчёт чисел по исходным данным, а не только чтение заявленного итогового значения.
- Проверяемую запись предметного рецензирования для диагнозов, эталонов и оценок пользовательских формулировок. Машина проверяет наличие, автора, дату, объект и отсутствие неразрешённых замечаний; это не заменяет предметную оценку.

Если исходник не предоставлен, проверка не выполнена. Отсутствующий знаменатель не даёт ноль процентов ошибок. Скриншот не заменяет код, пустая папка — набор данных, заголовок раздела — решение, а имя файла — работающую реализацию.

Описанные ниже поля являются предлагаемым контрактом для автопроверки. Их можно хранить в YAML/JSON, front matter или приложенной структурированной таблице с однозначным отображением полей. Машинная проверка использует зафиксированное отображение, а не свободное угадывание содержания Markdown. Формат и имена полей согласуются с владельцем артефакта; данный документ не утверждает, что такой формат уже принят в команде.

## 3. Общие проверки

Для каждого обязательного результата из разделов 4–7 проверяются:

| ID | Предикат приёмки | Доказательство |
|---|---|---|
| G-01 | Все указанные обязательные файлы существуют, непусты и читаются; число отсутствующих = 0 | Проверка путей относительно корня репозитория |
| G-02 | Для результата заданы owner, reviewer и artifact_path; owner и reviewer разрешаются в конкретных участников | Реестр команды и запись ответственности |
| G-03 | Все обязательные локальные ссылки разрешаются; повторяющихся ID внутри каждой сущности = 0 | Проверка ссылок, якорей и уникальности |
| G-04 | Все ссылки на use_case_id, adr_id, threat_id, test_id и eval_id разрешаются в соответствующие записи | Проверка внешних ключей между артефактами |
| G-05 | Область и числовые контракты каждого результата равны принятому решению Product; противоречий = 0 | Сравнение crop_ids, class_ids, input_organs, non_scope и metric_contracts |
| G-06 | Каждый вывод, заявленный как проверенный, имеет evidence_path; все пути существуют | Исходные результаты экспериментов, тестов или предметных проверок |

Неподтверждённые гипотезы допускаются как гипотезы. Утверждать проведение интервью, успешный эксперимент или достижение метрики без соответствующих доказательств нельзя.

| GD-06 | Контракт объёма отделяет сценарный eval от набора измерения качества; набор не объявляется подходящим для метрики при невыполнении её состава | Если сохраняется текущий PRD: для Macro-F1 ≥60 независимых бытовых фото и ≥15 каждого из 4 классов; негативные случаи добавляются отдельно. Старые 40 случаев не выдаются за этот набор |

Требование «30–50 пар» из плана первой лабораторной и минимум 60 для Macro-F1 в PRD нужно согласовать по назначению выборок. До решения нельзя молча увеличивать или уменьшать знаменатель, дублировать фото для квоты либо объединять данные настройки с финальным контролем.

## 8. Формат доказательства и итоговая приёмка

Для каждой проверки сохраняются artifact_path, criterion_id, expected, actual, evidence_path, checker, checked_at и основание вывода. Для выполненной команды дополнительно сохраняются команда, окружение и код завершения; для расчёта — входные данные и формула. Секреты в доказательства не включаются.

Пакет принимается, если общие и предметные проверки дали положительный результат, не осталось неразрешённых ссылок/блокирующих замечаний, а Product и команда подтвердили условия. Критерий неприменимости требует отдельной записи с причиной и согласующим; обязательный пункт задания нельзя исключить молча.

В репозитории уже доступны материалы первой лабораторной: PRD, бриф, гипотезы, исследования, глоссарий, прежние файлы Quality и dev-скелет. Это основание для проверки, но не доказательство наличия всех результатов второй лабораторной. Успешное чтение Compose не означает его успешный запуск; заглушка шлюза не означает работающее распознавание.

Согласование оформляется реальной записью решения. Этот документ не утверждает, что команда уже согласовала предложенные поля, ограничения или разрешила расхождение по культурам.
