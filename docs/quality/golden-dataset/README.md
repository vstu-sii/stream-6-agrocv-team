# Eval-набор AgroCV из сценариев использования

## Назначение и основание

Набор содержит **40 пар «вход → эталонное поведение»** для проверки системы до интеграции модели. Выбранный инструмент — приложенный `run_evals.py`, работающий с UTF-8 JSONL на Python 3.10+ без дополнительных библиотек. Он проверяет целостность набора, экспортирует входы и оценивает нормализованные ответы системы. Скрипт не вызывает модель и не отправляет данные в сеть.

Основание сценариев — `docs/prd.md`, `README.md` и `app/stub_gateway.py` из репозитория https://github.com/vstu-sii/stream-6-agrocv-team, снимок `731741a9cc62fbede43dfadb3deb9cd174b85033`. В этом снимке нет каталога `docs/use-cases/`. Поэтому UC-01–UC-08 в `use-cases.json` выведены из PRD и помечены как производные сценарии. Они не выдаются за согласованные use cases команды. После появления сценариев Product их ID и ветки сопоставляются с набором, а матрица покрытия пересчитывается.

Рабочий профиль здесь соответствует текущему PRD: **только листья яблони**, классы `healthy`, `apple_scab`, `black_rot`, `cedar_apple_rust`; `cannot_assess` — режим отказа, а не пятый класс. Результат предварительный, без назначения лечения. Более раннее обсуждение яблони и вишни этим файлом не переутверждается: расхождение должен разрешить Product с командой. Вишнёвые листья включены как неподдерживаемые входы именно для профиля PRD. При принятии двух культур эти карточки необходимо заменить, а не объявлять проходящими без изменений.

Один из диагностических листьев повторяется в тестах ошибок и неуверенности: это разные условия выполнения, а не новые независимые клинические образцы.

У выбранных оригиналов различаются группы листьев из авторского `leaf-map.json`; для Black rot в этой карте применяется прежнее имя `Apple_Frogeye Spot`. Это не подтверждает независимость деревьев: идентичность растений неизвестна. Изображения не сверялись с обучающим корпусом выбранной модели, сама модель пока не выбрана. Набор открыт разработчикам и не должен использоваться как доказательство независимого итогового качества.

## Что находится внутри

- `cases.jsonl` — 40 входов, ожидаемых полей, примеров ответа и рубрик проверки текста.
- `use-cases.json` — 8 сценариев со ссылками на разделы исходного PRD.
- `coverage.json` — связь UC → ID примеров.
- `assets/` — исходные фотографии с нейтральными именами.
- `fixtures/` — явно искусственные дефекты и негативные файлы.
- `sources/assets.jsonl` — источник каждого файла, исходная метка, группа листа, хеш и преобразование.
- `sources/attribution.json`, `sources/ATTRIBUTION.md` — авторы, лицензия и условия атрибуции.
- `schema.json` — описание формата карточки; `run_evals.py` дополнительно проверяет ссылки и согласованность.
- `CASES.md` — человекочитаемый перечень всех пар.
- `reviews/template.jsonl` — заготовка независимой проверки текста, без выдуманных проверяющих.
- `manifest.json` — фактический состав и назначение набора.
- `validation-report.json` — результат проверки структуры, не качество модели.
- `run_evals.py` — инструмент запуска проверок.

## Эталоны и пределы достоверности

Эталон диагноза для 24 обычных случаев взят **из опубликованной метки авторского датасета**, не из ответа проверяемой модели. Фотографии просмотрены на предмет наличия листа и читаемости файла. Специалист команды диагнозы ещё не подтвердил; это явно отражено в данных. Для приёмки по DoD необходима предметная проверка. Обнаруженный спорный снимок исключается или заменяется до оценки, а не переименовывается под ответ модели.

Тексты запросов — синтетические формулировки сценариев PRD; они не выдаются за интервью. Ожидаемые ответы — примеры поведения, а не рецепты лечения и не требование точного текстового совпадения. Для названий классов используются коды PRD; русские названия до публикации проверяет специалист.

`healthy` означает отсутствие видимых признаков поддерживаемых болезней на предоставленном листе. По нему нельзя утверждать здоровье всего дерева. Обоснованность отказов, их тон и понятность оцениваются по рубрике, а не только по слову `cannot_assess`.

Фото подготовлены в условиях исходного датасета, а не собраны в бытовом пилоте. Эти 40 сценариев **не заменяют** требуемые PRD минимум 60 независимых бытовых фото, по 15 каждого класса. Они также не измеряют North Star, p95 и стоимость. Пилот с пользователями и независимый контроль готовятся отдельно.

## Запуск

Распакуйте архив и перейдите в корневую папку, содержащую `docs/`. Команды одинаковы для macOS, Linux и Windows при доступной команде `python3` (в Windows при необходимости используйте `python`).

Проверка состава, хешей и связей:

```bash
python3 docs/quality/golden-dataset/run_evals.py validate
```

Экспорт входов без эталонов и исходных меток:

```bash
python3 docs/quality/golden-dataset/run_evals.py inputs --out inputs.jsonl
```

Проверка ответов подключённой системы:

```bash
python3 docs/quality/golden-dataset/run_evals.py evaluate --predictions predictions.jsonl --reviews text-reviews.jsonl --out report.json
```

`predictions.jsonl` создаёт адаптер вашей системы; действующий endpoint диагностики ещё не подключён к этому пакету. Скрипт не выдумывает предсказания. Пример формата одной записи (показан только как формат, не как результат модели):

```json
{"id":"EVAL-001","output":{"mode":"assessment","class_id":"healthy","reason":null,"treatment":null,"scope":"provided_leaf_only","preliminary":true,"next_step":"observe","message":"На этом листе не видно признаков поддерживаемых болезней; это не гарантия здоровья дерева."}}
```

Для `cannot_assess`, `input_error` и `service_error` поле `class_id` равно null. `reason` и допустимый `next_step` заданы в эталоне. Это нормализованный **eval-контракт**, а не якобы уже утверждённая схема OpenAPI. Когда команда подготовит `api/openapi.yaml`, адаптер явно отображает реальные ответы в этот формат. Он не должен дорисовывать отсутствующие у системы сообщение, ограничение или следующий шаг; передаётся реальное поведение.

Для четырёх невалидных файлов в предсказании дополнительно сохраняется `trace.model_called: false` из трассировки выполнения; одного сообщения об ошибке недостаточно для доказательства, что модель не вызывалась.

`output` не передаётся обратно модели. Вход модели — только `input`; `harness` исполняется испытательным стендом, ID нужен для объединения отчётов. Пути файлов разрешаются относительно папки набора. `provenance`, исходные имена с диагнозами и `expected` остаются у проверяющего.

## Особые условия выполнения

- EVAL-025–028 — контролируемые разрушения читаемости. Полное белое перекрытие — тест отсутствия визуальных данных, а не реальная болезнь. Параметры преобразований сохранены.
- EVAL-029–032 — неподдерживаемые культуры для выбранного профиля PRD; культура из авторской разметки скрыта от модели.
- EVAL-033–036 — проверка входной обработки до вызова модели. Большой файл содержит настоящий JPEG с добавленными нулевыми байтами после изображения; его размер 10 485 761 байт превышает и 10 MB, и 10 MiB. Это транспортная нагрузка, а не бытовой снимок такого размера.
- EVAL-037 — стенд принудительно возвращает уверенность ниже порога, выбранного AI Engineer на validation-данных. Число порога не подбирается по этому набору; вывод не оценивается по естественной уверенности конкретного фото.
- EVAL-038 — стенд делает шлюз недоступным.
- EVAL-039 — стенд задерживает шлюз на 21 секунду при тайм-ауте 20 секунд из PRD. Стенд отдельно проверяет фактическую задержку; этот JSONL-оценщик проверяет вид результата и сообщения, но сам не измеряет время.
- EVAL-040 — стенд возвращает явно помеченный ответ `stub: true`. Продукт не должен выдавать его за диагностику.

Без реализации fault-инъекций в стенде EVAL-037–040 нельзя считать реально выполненными. Простая подача их фото классификатору не воспроизводит сценарий.

## Как оценивается ответ

Машинная часть сравнивает режим, класс/причину, отсутствие лечения, границы вывода и допустимый следующий шаг. Полный словесный текст не сравнивается дословно. Все 40 ID обязательны; дубли, пропуски и лишние ID вызывают ошибку, а не исчезают из знаменателя.

Смысловая проверка сообщения проводится независимым проверяющим по четырём пунктам `expected.text_rubric`. В `text-reviews.jsonl` указываются id, reviewer, checked_at и четыре булевых решения в rubric. Пустая заготовка в `reviews/template.jsonl` **не является проведённой проверкой**. Проверяющий читает фактическое `message`, а не только структурированные поля. В случае разногласий привлекается второй участник.

Без заполненной проверки текста скрипт сообщает только результаты структурной части и число непросмотренных сообщений. Полное прохождение случая не присваивается автоматически. Самооценка модели не заменяет внешнюю проверку. Код завершения 0 означает прохождение всех проверок, 2 — неполное/неуспешное прохождение, 1 — ошибку формата или целостности.

## Проверки контекста

В текущем PRD выбрана классификация изображения и справочная карточка; поиск документов (RAG) не определён. Поэтому фиктивный retrieval-контекст в случаи не добавлен. Источники меток в `provenance` не являются контекстом для модели.

Если команда выберет ответы по найденным документам, перед использованием соответствующего сценария добавляются отдельные случаи: правильный контекст, отсутствующий нужный документ, конфликтующие сведения и вредоносная инструкция в документе. У них должны быть query, corpus/document IDs, ожидаемые найденные фрагменты и отдельно рубрика опоры итогового ответа на контекст. Прежний поиск нельзя считать проверенным одним совпадением итогового текста.

## Владелец и пополнение

Владелец набора — участник роли **Quality & Safety, выполняющий эту лабораторную работу**. Его имя/аккаунт команда добавляет в запись назначения; фиктивные имена не используются. Product подтверждает соответствие UC и область продукта, AI Engineer — отображение классов и условия модельных проверок, предметный рецензент — корректность диагнозов. Delivery подключает адаптер, трассировку и fault-инъекции.

Процесс добавления:

1. Зафиксировать новый или изменённый UC и его источник. Не добавлять записи только для увеличения количества.
2. Получить фото с разрешённым использованием; сохранить автора, точный источник, хеш и группу листа/растения.
3. Установить эталон независимо от проверяемой модели; получить предметную проверку и разрешить разногласия.
4. Назначить новый ID, связать его с UC, заполнить поля входа, ожидаемые элементы, запреты и рубрику. Синтетическое преобразование сохранить вместе с параметрами.
5. Обновить manifest и coverage; выполнить `validate`, проверить дубликаты и пересечения с обучением.
6. Сохранить принятое решение и причину включения в журнале изменений данных. После использования случая при настройке не считать его независимым test.

Текущий архив подготовлен отдельно от командного репозитория. Никаких коммитов, push, PR или изменений в GitHub не выполнялось.
