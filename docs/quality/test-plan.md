# Тест-план AgroCV

## Объект и условия

Проверяем загрузку фото → обработку → предварительный результат либо отказ/ошибку. Рабочий профиль — текущий [PRD команды](https://github.com/vstu-sii/stream-6-agrocv-team/blob/main/docs/prd.md): листья яблони, четыре класса, без назначения лечения. Расхождение с прежним охватом яблони и вишни разрешает Product; до решения профиль не расширяем автоматически.

Основа: [DoD](dod.md), [40 eval-случаев](golden-dataset/cases.jsonl), [покрытие UC](golden-dataset/coverage.json), [инструкция оценщика](golden-dataset/README.md). UC-01–08 выведены из PRD и требуют сопоставления со сценариями Product. Код, модель, предобработка, данные и конфигурация фиксируются перед прогоном; эталоны проверяются до просмотра предсказаний. Адаптер API и fault-инъекции ещё предстоит реализовать.

## Уровни проверок

| ID / уровень | Вход и действие | Ожидаемый результат / доказательство |
|---|---|---|
| T-01 · unit: файл | Пустые/повреждённые байты, TXT, JPEG/PNG, размер ниже/на/выше лимита | Принимаются только допустимые файлы; остальные отклонены до модели. Лимит в байтах закреплён в OpenAPI; EVAL-033–036, трасса model_called=false |
| T-02 · unit: решение | Подать четыре класса, оценку ниже/на/выше порога, неизвестную метку, stub=true | Согласованная классификация либо cannot_assess/ошибка; отказ не равен healthy. Порог выбран на validation; EVAL-037,040 |
| T-03 · unit: оценщик | Валидный/изменённый manifest, хеши, дубли ID, отсутствующие ответы, неверный класс | Нарушения обнаружены; пропуски не исключены из знаменателя; нет полного зачёта без внешней проверки текста |
| T-04 · интеграция | Отправить файл по принятому OpenAPI через предобработку в управляемый шлюз | Схемы запроса/ответа соблюдены; эталон и диагноз из имени файла не передаются модели. Все варианты UC-01–06 |
| T-05 · интеграция: сбои | Сделать шлюз недоступным; задержать ответ на 21 с; вернуть заглушку | Понятная ошибка, class_id=null, возможность повторить; тайм-аут 20 с. EVAL-038–040; трасса, длительность и ответ |
| T-06 · интеграция: UI | Пройти загрузку, ожидание, результат, пересъёмку, отказ и ошибку | Каждая ветка UC представлена; нет диагноза другого органа, назначения лечения или гарантии здоровья. Протокол и снимки экрана |
| T-07 · evals | Выполнить EVAL-001–040 с реальным адаптером и заданными fault-инъекциями | 24 известных класса, 4 плохих фото, 4 чужие культуры, 4 невалидных файла, 1 неуверенность, 2 сбоя, 1 stub. Все 40 ID учтены; отчёт оценщика и внешний разбор сообщений |
| T-08 · качество | Отдельный независимый бытовой test: ≥60 фото, ≥15 каждого класса | Macro-F1 ≥0,80; матрица ошибок и F1 классов. Отказ на известном классе — ошибка: FN истинного класса без TP; unknown не становится пятым классом |
| T-09 · нагрузка/цена | ≥100 запросов, 5 одновременных пользователей; собрать время и расходы | p95 ≤10 с от приёма файла сервером до результата; стоимость ≤0,50 ₽/принятый запрос при 1 000/месяц; условия ниже |
| T-10 · безопасность | Повторить проверки для каждого поля API/UI и каждой выбранной меры [модели угроз](threat-model.md) | Для каждой меры есть threat_id → test_id, вход и проверяемый исход; секреты/полные фото не попадают в публичные логи. Проверить удаление фото по согласованному сроку |

Для T-09: p95 — элемент `ceil(0.95×N)` отсортированных длительностей; ошибки/тайм-ауты учитываются и публикуются отдельно, не скрываются отбором успешных запросов. Передача файла по сети измеряется отдельно. Цена — все инфраструктурные расходы обработки за период, включая простой и ошибки, / все принятые запросы; обучение и труд отдельно. Без трафика цена не определена. Отдельный пилот North Star: ≥30 сессий, ≥5 участников, ≤6 сессий на участника, цель ≥80%; условия успешной сессии — строго из PRD. Его не заменяют evals.

## Автоматизация с лабораторной 3

**Каждый PR:** сохранить существующие Ruff, format, Docker build, Compose config и health-smoke; добавить T-01–05, проверку JSON/OpenAPI и связей UC/eval, валидацию всех 40 карточек. Управляемый шлюз проверяет маршрутизацию и ошибки, но не качество модели. Тайм-ауты в быстрых unit-тестах проверять управляемыми часами; реальное время — интеграцией.

**Перед выпуском/при смене модели:** T-06–10, полный T-07 с закреплённой моделью, независимый T-08, нагрузка и предметная проверка текста. После появления адаптера запускать `run_evals.py evaluate`; до него доступен только `run_evals.py validate`. Неподключённую обязательную проверку нельзя считать успешной. GitHub в рамках подготовки плана не изменяется.

## Приёмка и ответственность

Unit/интеграционные проверки — 100% обязательных assertions; функциональные evals — 40/40 по нормализованному и внешнему текстовому контракту. Пороги T-08–09 не подменяются успехом сценарных тестов; 40 лабораторных случаев не являются 60 бытовыми фото. Любое необоснованное лечение, утечка, выдача stub за диагноз или провал критического отказа блокируют приёмку. При изменении модели повторяются затронутые проверки и регрессия.

Delivery отвечает за unit/интеграцию/CI и трассировку; AI Engineer — модель, порог и замеры; Quality — набор, оценку и отчёт; Product — UC и пользовательские критерии. В отчёте: run_id, конфигурация, ID теста/случая, фактический результат, входные измерения, доказательство и проверяющий. Это план: фактические прогоны приложения и достижение метрик не заявляются.
