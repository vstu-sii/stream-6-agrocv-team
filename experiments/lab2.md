# Lab 2 — спайки рискованных допущений

Дата: 2 ноября 2026 года. Приложение: [lab2_spikes.py](lab2_spikes.py). Основания: [lab1](lab1.md), [AI-пайплайн](../ai-pipeline.md), [ADR выбора моделей](../model-candidates.md).

**Итог: проверка контракта сработала иначе, чем предполагалось.** Валидатор lab1 принимает три специально созданных нарушения контракта; короткое усиление отклоняет их. При этом даже усиленная проверка принимает структурно корректный, но неверный относительно метки диагноз. Новый инференс Qwen и сравнение 4B/2B здесь **не выполнены**: в доступном окружении нет PyTorch/Transformers и новых размеченных случаев. Это отчёт о выполненном программном спайке и подготовленном диагностическом спайке, а не о двух успешных GPU-экспериментах.

| Допущение | Что уже известно | Риск и способ проверки |

Выбраны A и B: A можно проверить сейчас, B ограничивает любые заявления о диагностическом качестве. Автономность, RAG, SAM и дообучение в этот опыт не добавляются.

## 2. Спайк A — достаточно ли текущей проверки JSON?

**Вопрос:** отклоняет ли валидатор ответы, нарушающие согласованный контракт?

**Метод:** взять три `raw_answer` из исходного архива lab1; отдельно создать восемь испорченных вариантов первого ответа. Сравнить неизменённый `validate_answer` из runner lab1 и экспериментальную проверку, дополнительно запрещающую повторные ключи JSON, дубли альтернатив и основную гипотезу среди альтернатив. Ожидание: исходные ответы проходят, каждый испорченный отклоняется. Это тест программы, а не новые ответы модели.

**Фактически выполнено без GPU:**

| Вход | Валидатор lab1 | Усиленная проверка |
|---|---|---|
| Три исходных ответа | Принял 3/3 | Приняла 3/3 |
| Markdown-обёртка, обрезанный JSON, неизвестный класс, противоречие status/disease, неверный тип status | Отклонил 5/5 | Отклонила 5/5 |
| Дубли alternatives, основной диагноз в alternatives, повторный ключ status | **Принял 3/3** | Отклонила 3/3 |
| Подмена `apple_scab` на допустимый `apple_rust` с очисткой alternatives | Принял | **Приняла** |

Последняя строка — синтетический отрицательный контроль: подмена противоречит предоставленной пользователем метке парши, но соответствует схеме. **Это не ошибка, допущенная Qwen в новом запуске.**

**Результат: сработало иначе.** JSON полезен для интеграции, однако прежнего валидатора недостаточно для нового строгого контракта ADR. Усиленная проверка закрывает обнаруженные структурные пропуски; правильность диагноза и обоснованность наблюдений она не проверяет. Набор из восьми нарушений не доказывает полноту валидации.

**Решение:** перенести требования к уникальности в будущую Q3-проверку; сохранять сырой ответ и причину отказа, не «исправлять» диагноз парсером. Экспериментальный код не заменяет валидатор приложения. Проверка Q4 на размеченных фото остаётся обязательной.

### Повторение A

Нужны Python 3.11+, исходный архив результатов и прежний `qwen_probe/run_probe.py`. Режим `audit` использует только стандартную библиотеку; установка модели не нужна. Команды выполняются из корня проекта, путь к архиву замените на свой:

```cmd
python docs\experiments\lab2_spikes.py audit --archive "upload\20261025T125538_983444Z.zip" --output "runs\lab2\audit.json"
```

При другом расположении runner задайте `--runner "путь\run_probe.py"` **перед** словом `audit` или `run`. Скрипт не распаковывает архив на диск и не меняет исходные журналы.

## 3. Спайк B — переносится ли результат на новые случаи?

**Один вопрос:** сохраняет ли фиксированный промпт 4B полезную диагностическую гипотезу и корректный отказ за пределами листа из lab1?

**Статус: подготовлен, не выполнен.** Новых диагностических результатов, скорости 2B и сравнения качества пока нет.

Минимальный разведочный набор — 18 независимых фото: по два для каждого из пяти целевых классов; по два для каждой культуры без видимых симптомов; ещё два с нецелевыми повреждениями и два неинформативных снимка, по одному каждой культуры. Классы — как в lab1: `apple_scab`, `apple_rust`, `apple_powdery_mildew`, `cherry_leaf_spot`, `cherry_powdery_mildew`. Для остальных случаев использовать соответственно `no_visible_symptoms`, `other_or_unknown`, `insufficient_image`. Отсутствие симптомов не означает доказанное здоровье.

Экспертные метки и их происхождение фиксируются **до** прогона. Не использовать дубликаты, кропы одного листа как независимые случаи или фотографии, на которых подбирался промпт. Метки сохраняются для оценки и не передаются Qwen. Пример одной записи `lab2_cases.json` (нужен полный JSON-массив всех случаев):

```json
[
  {
    "id": "apple_scab_01",
    "crop": "apple",
    "image": "images/apple_scab_01.jpg",
    "label": "apple_scab"
  }
]
```

Фото ищутся относительно manifest. Дополнительные сведения о происхождении меток хранить рядом отдельно. Скрипт проверяет наличие меток, но их экспертность и независимость снимков проверяются вручную.

Запуск на пользовательской RTX 3060, в проверенном окружении lab1; пути к локальным snapshot замените на свои. Один случай — один вызов, один промпт, без SAM, истории и автоматических повторов:

```cmd
python docs\experiments\lab2_spikes.py run --manifest lab2_cases.json --model "D:\models\Qwen3-VL-4B-Instruct\snapshots\ebb281ec70b05090aa6165b016eac8ec08e71b17" --revision ebb281ec70b05090aa6165b016eac8ec08e71b17 --output runs\lab2\4b
```

Используется неизменённый runner lab1: локальный режим, NF4, прежний промпт, до 589 824 пикселей и 384 новых токенов, контекст до 4096. Он записывает `run.json`, `results.jsonl`, `summary.md`; параметры, хеши фото, полный промпт, ответы, ошибки, время и память сохраняются. Указанный revision для локального каталога — запись происхождения: соответствие содержимого snapshot этому commit необходимо проверить заранее. Ветка `run` ещё не проверена на GPU; усиленный валидатор A в неё намеренно не внедрён, чтобы сохранить исходный baseline.

**Правило решения до запуска:** любое ложное «нет симптомов» на больном листе, диагноз на явно неинформативном фото или неподдержанное ключевое наблюдение — повод остановить расширение интерфейса и разобрать случай. Отдельно считать совпадения с эталоном, ошибки JSON, отказы и ошибки каждого класса. Ошибки выполнения входят в общий знаменатель; при незавершённом запуске указывать число выполненных случаев из запланированных. Даже отсутствие ошибок на 18 фото означает лишь «явный провал не обнаружен», а не доказанную точность.

После прогона записать: «сработало / не сработало / сработало иначе», конкретные case_id, предсказания и эталоны. До появления журналов это поле остаётся **«не проверено»**.

## 4. Деградация и цена спайка

2B пока не допущена. После B выполнить отдельный парный опыт, повторив команду с локальным snapshot 2B, его фиксированным revision и `--output runs\lab2\2b`. Дождаться завершения процесса 4B; не менять одновременно разрешение, промпт или данные. Малый набор выявляет грубую регрессию, но не позволяет подтвердить небольшие различия macro-F1/recall из [ADR](../model-candidates.md): для допуска требуется расширенный тест и согласованные абсолютные пороги.

До допуска резерва: OOM/ошибка → технический отказ без диагноза; неизвестные признаки → неопределённость; плохое фото → запрос другого снимка. Не запускать 2B ради более уверенного ответа. После допуска переключение только явное, отдельным запросом. Приложение спайка не реализует watchdog или восстановление worker: зависший процесс завершать вручную, timeout пока не считать проверенным.

**Цена:** ручная разметка и разбор ошибок, время GPU, хранение локальных snapshot и журналов. Для разведочного B — 18 вызовов 4B; отдельное сравнение добавит 18 вызовов 2B. Входной бюджет не более 3712 токенов и выход до 384 на вызов; это потолки, не фактический расход. Платных API нет.

Код приложения одноразовый: он повторно использует экспериментальный runner, а не создаёт сервис. После ответа на вопросы его исполнение прекращается; сохраняются журналы, метки и выводы. В продукт переносим проверенные настройки и требования к контролю, но не эту оболочку запуска.
